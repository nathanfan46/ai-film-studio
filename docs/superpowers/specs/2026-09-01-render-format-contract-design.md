# Render Format Contract & Robust Final Render — Design

## Problem

Two related issues, discovered together:

1. `render.py`'s `render()` uses the ffmpeg concat demuxer with `-c copy`,
   which requires every input clip to have an identical stream layout. Real
   projects mix silent shots (no dialogue) with shots carrying voice/sfx/
   lipsync audio — when the concat demuxer hits that mismatch it doesn't
   error, it silently produces a video-only output. `ai-film render`
   reported success (`rendered ...`) on a fully audio-less final file. Shots
   generated by different video models also differ in native resolution
   (veo-3: 1280x720, hailuo-2.3: 1408x768/1376x768, h3-max: 1344x768/
   1376x768) — `-c copy` concat can't handle that either; it fails loudly
   rather than silently, but it still blocks a render that should succeed.

2. The root cause is upstream of render: `shot.json` never declares a
   target production resolution/fps, so every video model is free to
   return whatever its own defaults or input-image dimensions dictate.
   Render-time normalization is a necessary defensive layer regardless
   (providers can misbehave, schemas can change, artifacts can be
   hand-replaced), but treating render as the *only* place resolution is
   ever considered means every mismatch is discovered after the fact
   instead of declared as an intent up front.

## Goals

- Never silently lose audio, and never hard-fail, when concatenating clips
  with mismatched audio presence or resolution at render time.
- Give a project a canonical target resolution/fps, declared once, that
  every shot inherits by default — without forcing per-shot busywork for
  existing shots.
- Ask each provider for its closest native approximation of that target.
  No provider used by this project accepts an exact pixel width/height
  (verified against fal's own OpenAPI schemas — see "Provider format
  capabilities" below), so "send the resolved value to the provider" means
  per-model translation, not a literal passthrough field.
- Detect and record drift between what was requested and what a provider
  actually returned, instead of silently accepting it.
- Never touch `one-more-life` (the live project) or `.env` while building
  or testing this — both stay untouched and ungitignored, per this
  project's standing rule.

## Non-goals (v1)

- Migrating or mutating existing `shot.json` files to add `format`. Legacy
  shots resolve their format from `config.json`'s `render` defaults purely
  at generation time; their files on disk are never rewritten by the
  engine.
- Aspect ratios beyond 16:9. The design must not block adding 9:16/1:1
  later (the resolution string and per-model aspect-ratio derivation are
  already ratio-agnostic), but v1 ships and tests only the project's
  current 16:9 default.
- Smart/content-aware cropping. Both render-time clip normalization and
  the new reference-image pre-resize step always letterbox (scale-to-fit
  + pad), matching what render.py's manually-verified one-off fix already
  did.

## Provider format capabilities (verified via fal's OpenAPI schemas)

| Model | Resolution control | Aspect ratio control |
|---|---|---|
| `veo-3` | `resolution`: `720p`/`1080p` enum | `aspect_ratio`: `auto`/`16:9`/`9:16` enum |
| `h3-max` | `resolution`: `480P`/`768P` enum | none directly — "output aspect ratio follows `image_url`" |
| `hailuo-2.3` / `hailuo-2.3-fast` | none | none — dimensions are dictated entirely by the input reference image |
| `nano-banana` (image) | none | `aspect_ratio` enum (`21:9`…`9:16`) |

No model accepts literal width/height. This is why the design below treats
`format.resolution` as a **canonical target**, not a guarantee, and gives
each provider adapter the job of deriving its own nearest native
parameters — the same shape as the duration-snapping (`_snap_duration`/
`_duration_field`) pattern `providers/fal/video.py` already has for clip
length.

None of these schemas expose an fps field either — every model's frame
rate is a fixed, undocumented native value, the same situation this
codebase already has for `hailuo-2.3-fast`'s clip duration (see
`_NO_DURATION_FIELD_MODELS`). `target_fps` is therefore never sent to a
provider; it only participates in post-generation mismatch detection
(Section 4) and in render.py's own `fps=F` normalization filter (Section
5), which is the one place fps actually gets enforced.

## Design

### 1. Canonical format contract

`config.json`'s `render` section gains three keys, replacing today's empty
`{}` default in `project.py`'s `DEFAULT_CONFIG`:

```json
"render": {
  "resolution": "1280x720",
  "fps": 24,
  "strict_format": false
}
```

`shot.json`'s schema (`schema.py`) gains an **optional** top-level `format`
object:

```json
"format": {
  "resolution": "1280x720",
  "fps": 24
}
```

Optional, not required — `one-more-life`'s existing shots keep validating
and generating with zero edits. Going forward, `ai-film-storyboard.md` is
updated to populate `format` explicitly (resolved from `config.json`'s
`render` defaults at authoring time) on every new shot it writes, so new
shots become self-contained production contracts; only pre-existing shots
ever rely on the runtime fallback below.

### 2. Resolving the target format at generation time

New helper `_resolve_target_format(path, shot_data) -> tuple[int, int, int]`
(width, height, fps) in `cli.py`, alongside the existing `_video_duration`/
`_video_model` helpers, checked in this order:

1. `shot_data["format"]["resolution"]`/`["fps"]`, if present — parsed via a
   shared `parse_resolution("1280x720") -> (1280, 720)` helper.
2. else `config.json`'s `render.resolution`/`render.fps`.
3. else the hardcoded engine default `(1280, 720, 24)` — so a project whose
   `render` config is still `{}` (e.g. `ai-film init`'d before this change
   shipped, or never touched since) doesn't break.

This resolved target threads into `generate_video_service`/
`generate_image_service` via new `target_width`/`target_height`/
`target_fps` fields on `VideoGenerationRequest`/`ImageGenerationRequest`
(`models.py`), used both to build native provider params (Section 3) and
to validate the actual artifact afterward (Section 4).

### 3. Provider adapters derive native params from the target

New per-provider helpers in `providers/fal/video.py`, mirroring
`_snap_duration`/`_duration_field`:

```python
def _nearest_aspect_ratio_enum(width: int, height: int, allowed: set[str]) -> str:
    """Reduce width:height to its simplest ratio and pick the closest
    allowed enum value by numeric ratio distance — same snap-to-nearest
    idea _snap_duration already uses for clip length."""

def _video_format_fields(model: str, width: int, height: int) -> dict:
    """Native resolution/aspect_ratio fields for a model's request body,
    derived from the canonical target. Empty dict for models with no such
    fields at all (the hailuo family), which rely entirely on the resized
    reference image (below) instead."""
```

`_video_format_fields`'s output is merged into `submit()`'s `input_data`,
the same place `_duration_field`'s result already goes. `providers/fal/
image.py` gets the equivalent `_image_format_fields(model, width, height)`
for `nano-banana`'s `aspect_ratio` field.

For models whose aspect ratio is dictated by the input image
(`h3-max` and both `hailuo` models — `veo-3` is excluded, since its own
`aspect_ratio` field already covers it without touching the reference), a
new `_resize_reference_for_target(image_path: Path, width: int, height:
int) -> Path` in `providers/fal/video.py` reuses the exact ffmpeg filter
chain render.py's clip normalization uses (`scale=W:H:
force_original_aspect_ratio=decrease,pad=W:H:(ow-iw)/2:(oh-ih)/2,setsar=1`)
against a single still frame, writing a throwaway temp file that gets
uploaded in place of the raw reference path. Gated by a new
`MODELS_REQUIRING_RESIZED_REFERENCE = {"h3-max", "hailuo-2.3",
"hailuo-2.3-fast"}` set, checked in `submit()` right before
`client.upload_file()`.

### 4. Post-generation validation

After `get_result()` downloads the artifact, `generate_video`/
`generate_image` in `generation_service.py` probes the actual file (new
shared `probe_resolution(path) -> tuple[int, int]`, following this
codebase's established convention of a small ffprobe helper duplicated
per module rather than centralized — see `_probe_duration`/
`_has_audio_stream` in `video_diagnostics.py`/`video_fix.py`) and compares
the exact `(width, height, fps)` tuple against the resolved target. No
tolerance band or "close enough" heuristic — per the provider capability
table above, no model can hit the literal target pixel-for-pixel, so an
exact-equality check will flag a mismatch on most real generations by
design. That is expected and intentional: it's precisely what makes
`strict_format=false`'s default behavior ("warn, don't block") the right
default, and it's what gives `strict_format=true` real teeth (a genuine,
unambiguous non-negotiable check) once a production needs one:

- **Exact match**: proceed, no note.
- **Mismatch, `strict_format=false` (the default)**: the artifact dict
  gains `"requested_format": {"width": .., "height": .., "fps": ..},
  "actual_format": {"width": .., "height": .., "fps": ..},
  "format_mismatch": true`; a warning is printed but generation is marked
  `completed` as normal. This mirrors how duration snapping already
  behaves — a provider not hitting the literal requested value is expected
  behavior, not an error.
- **Mismatch, `strict_format=true`**: raise the existing `ProviderError`
  (already caught by `_run_generation`'s try/except in `cli.py`) —
  generation is marked `failed`, no artifact is persisted, exactly like
  any other provider failure today.

### 5. `render.py` stays the defensive final boundary

- Replace concat-demuxer + `-c copy` with `filter_complex` + re-encode:
  every clip gets `scale=W:H:force_original_aspect_ratio=decrease,
  pad=W:H:(ow-iw)/2:(oh-ih)/2,setsar=1,fps=F`; each clip's audio is passed
  through or replaced with an `anullsrc` pad sized to that clip's *real*
  ffprobe'd duration (not the shot's static `duration_seconds`, which this
  project already knows can drift from the actual file); then
  `concat=n=N:v=1:a=1`; output re-encoded `libx264`/`aac`.
- `W, H, F` for render come from `config.json`'s `render.resolution`/
  `render.fps` (defaulting to 1280x720/24) — render always targets one
  canonical deliverable size regardless of what any individual shot
  declared or a provider actually returned; there is no per-shot override
  at render time.
- `_escape_concat_path` and the concat-list file are removed. ffmpeg
  inputs become direct subprocess argv elements (list form, not a shell
  string), so there is nothing left to shell-escape.
- New `preflight_warnings(manifest, project_dir) -> list[str]`: non-fatal,
  ffprobe-based, reports the spread of actual clip resolutions and which
  shots have no audio stream. Printed by `render_cmd`, never blocks —
  render's own normalization already handles both cases correctly.

### 6. Testing

- `providers/fal/video.py`/`image.py`: tests confirming each model's
  request body gets the right native fields for a given target (same
  style as the existing `test_h3_max_sends_integer_duration_and_prompt_
  expansion_mode`); a real-ffmpeg test for `_resize_reference_for_target`
  asserting the output has the target's exact pixel dimensions regardless
  of the source image's own shape.
- `generation_service.py`: mismatch-detection tests for both
  `strict_format` values, using a mock provider whose returned artifact's
  real (ffprobe'd) size differs from the resolved target.
- `render.py`: real-ffmpeg tests mixing (a) clips of different native
  resolutions, (b) silent and audio-bearing clips in the same render,
  asserting the final output has both video and genuinely non-silent
  audio; `preflight_warnings` tests for both mismatch kinds.
- `cli.py`: `_resolve_target_format`/`parse_resolution` tests — shot.json
  format present, absent with a configured `render` fallback, absent with
  an empty `render: {}` (hardcoded default).
- Full suite must stay green throughout (358 passing as of this spec).

### 7. Docs

- `README.md`: remove/update the "`render` drops audio" Known Limitation
  bullet (now fixed); document `render.resolution`/`render.fps`/
  `render.strict_format` and `shot.json`'s optional `format` field in the
  command reference / project layout sections.
- `.claude/agents/ai-film-storyboard.md`: add an instruction to populate
  `format` (resolved from `config.json`'s `render` defaults) when
  authoring a new shot's JSON.
- `.claude/agents/ai-film-media.md`: brief note that an artifact's
  `format_mismatch: true` flag, when present, is informational — surfaced
  to the human only if they ask about visual inconsistency, not something
  the agent should act on unilaterally.

## Open risk, flagged not resolved

`_resize_reference_for_target` is the least-verified part of this design —
it changes what image bytes actually get sent to three of four video
models on every call, and its correctness can only be fully confirmed by a
real (paid) fal generation, not schema inspection alone. Implement and
unit-test it thoroughly, but treat the first few real generations after
this ships as a deliberate verification pass — the same way this
project's `prompt_optimizer=false` fix was verified against a real fal
call before being trusted, rather than assumed correct from the schema
alone.

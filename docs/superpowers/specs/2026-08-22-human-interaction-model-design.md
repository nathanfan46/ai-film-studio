# Human Interaction Model — Design

**Status:** Approved for implementation (first slice)
**Date:** 2026-08-22

## 1. Overview

The core engine (`ai_film` CLI, see `docs/superpowers/specs/2026-08-18-ai-film-studio-design.md`
and `docs/superpowers/plans/2026-08-18-ai-film-studio-core-engine.md`) is a deterministic,
one-shot batch pipeline: generate once per shot, check status, render. It has no concept
of reviewing a generated asset, comparing alternatives, or refining one through
discussion — every `generate-*` command produces exactly one artifact and exits.

This spec closes that gap by adding a reusable **propose → review → refine → lock**
loop: generate several candidates, display them in a local browser gallery, let the
user pick and discuss changes in chat, refine the pick via true image editing (or
prompt-based regeneration where editing isn't available), and lock the final choice
into the artifact location the existing engine already reads. The loop is designed
once, generically, so it applies identically to characters, shot storyboards, shot
video, and (later) audio and whole-film preview — not five bespoke review flows.

### Goals

- One data model (`CandidateSet`) and one set of CLI primitives that support
  multi-candidate generation, browser review, discussion-driven refinement, and
  locking-in a final choice — usable for any generation target (character, shot
  image, shot video, audio, whole-film preview) without redesign.
- The candidate layer sits entirely upstream of the existing artifact-write point:
  `shot.json`'s `generation.<stage>.artifact`, `render`, `preflight`, `status`, and
  every other already-built, already-tested piece of the core engine needs zero
  changes and stays unaware candidates exist.
- Candidate generation goes through the same cost gate, retry/backoff, and logging
  plumbing every other generation call already uses — no parallel/bypass path.
- Story and character *brainstorming* (the text discussion — personality, genre,
  style reference, converging on a brief) is pure agent/chat design, not new CLI
  surface; it produces the inputs (`--prompt`, `--action`, etc.) fed into candidate
  generation.

### Non-Goals (this spec, first implementation slice)

- Video/audio candidate review is designed here (same commands, different
  `--target`/`--stage`) but not built in the first slice — only image candidates
  (character references, shot storyboards) are exercised.
- Whole-film final-cut preview, subtitles, and audio muxing into `render` are known
  gaps (documented in the core engine README's Known Limitations) that this loop's
  design accommodates but does not implement yet.
- Interactive/clickable browser review (pick-by-click in the page). The gallery is
  a *display* surface; picking and feedback happen in chat, per explicit decision.
- Publishing/distribution (YouTube upload, etc.) — explicitly deprioritized by the
  user, not addressed by this spec at all.
- Direct MCP-based generation for candidates. The `fal-ai-media` MCP remains
  exploration-only per the core engine spec; candidate generation is real spend and
  must go through the cost-gated CLI, not bypass it.

## 2. Architecture

```
                    Character/Director Agent (chat)
                              │
              ┌───────────────┼────────────────────┐
              ▼               ▼                     ▼
   generate-candidates    review              edit-candidate
   (cost-gated, N imgs)  (build+open HTML)   (cost-gated, submit_edit
              │               │               or prompt-regenerate)
              ▼               │                     │
       CandidateSet ◄─────────┴─────────────────────┘
       (candidates.json + candidates/*.png)
              │
              ▼ select-candidate
       canonical artifact location
       (assets/.../reference.png, or
        shot.json generation.<stage>.artifact)
              │
              ▼
   ── everything already built reads from here, unchanged ──
       render / preflight / status / generate-video (as a
       reference input) / etc.
```

**Core principle:** the candidate layer is a new stage *before* artifact-write, not
a replacement for it. Every command and schema field the core engine plan already
built and tested (`shot.json`'s `generation.<stage>.artifact`, `render`'s manifest,
`preflight`, `status`) is untouched by this spec. Downstream code has no idea
candidates exist — it only ever sees a final, selected artifact, exactly as today.

## 3. The `CandidateSet` Data Model

One `CandidateSet` per generation target. Stored alongside the target's existing
location in the project tree:

```
assets/characters/<name>/
├── candidates.json
├── candidates/
│   ├── 001.png
│   ├── 002.png              # e.g. an edit of 001
│   └── review.html          # generated by `ai-film review`
└── reference.png            # copy of the selected candidate, once locked

04_storyboard/candidates/<shot_id>/
├── candidates.json
├── candidates/{001,002,...}.png
└── candidates/review.html
```

`candidates.json` shape:

```json
{
  "target": "character:girl",
  "candidates": [
    {
      "id": "001",
      "path": "candidates/001.png",
      "provider": "fal",
      "model": "nano-banana",
      "prompt": "a girl, cinematic sci-fi style, ...",
      "parent": null,
      "created_at": "2026-08-22T10:00:00Z"
    },
    {
      "id": "002",
      "path": "candidates/002.png",
      "provider": "fal",
      "model": "nano-banana",
      "prompt": "black jacket instead of white",
      "parent": "001",
      "created_at": "2026-08-22T10:05:00Z"
    }
  ],
  "selected": null
}
```

- `target` identifies what this set is for: `character:<name>`, `env:<name>`, or
  `shot:<id>:<stage>` (e.g. `shot:S01_SH01:image`).
- `parent` is set when a candidate was produced by editing another candidate
  (via `submit_edit`) rather than generated fresh — this preserves edit lineage
  so the discussion history is visible, not just the final pick.
- `selected` holds the chosen candidate's `id` once `select-candidate` runs, or
  `null` before a pick is made. This field, not any state in `shot.json` or
  `assets/`, is the source of truth for "has this target been locked yet."

## 4. Provider & Engine Changes

Two additions to the provider layer from the core engine (`src/ai_film/`), kept
minimal and additive — no existing provider method signatures change.

**`num_candidates` on generation requests.** `ImageGenerationRequest`,
`VideoGenerationRequest`, and the audio request dataclasses gain an optional
`num_candidates: int = 1` field. `FalImageProvider`'s hardcoded `"num_images": 1`
becomes `"num_images": request.num_candidates`. Whether the result is written to
the candidate pool or straight to `generation.<stage>.artifact` is decided by
which CLI command/service function was called, not by inspecting the request —
`generate-candidates` is new code in `src/ai_film/services/candidate_service.py`
that always writes to the pool; the existing `generate-image`/etc. commands keep
calling `run_generation_stage` unchanged and never set `num_candidates` above 1.
The two code paths share provider construction and job execution but never share
a write path.

**`submit_edit()` on `ImageProvider`, optional.** A new Protocol method:

```python
class ImageProvider(Protocol):
    def submit(self, request: ImageGenerationRequest) -> GenerationJob: ...
    def poll(self, job: GenerationJob) -> JobStatus: ...
    def get_result(self, job: GenerationJob) -> ImageGenerationResult: ...
    def submit_edit(self, base_image_path: str, instruction: str) -> GenerationJob:
        raise NotImplementedError
```

`FalImageProvider` implements it against fal's image-editing endpoint (nano-banana
supports image-to-image editing). `VideoProvider`/`AudioProvider` do not gain this
method in v1 — editing falls back to prompt-based regeneration, decided entirely
in the **service layer**, not the provider interface: the service checks whether
the resolved provider implements `submit_edit` (a plain `hasattr`/try-except
around `NotImplementedError`) and, if not, calls `submit()` again with the
original prompt plus the user's edit instruction appended.

## 5. New CLI Commands

Layered on the existing generation service (`src/ai_film/services/generation_service.py`)
— same cost-gate-first, retry, logging plumbing every existing `generate-*` command
already uses. No new plumbing invented; these commands call the same
`run_generation_stage`-style machinery with a different sink (candidate pool
instead of `generation.<stage>.artifact`).

- **`ai-film generate-candidates --target <target> --count N [--prompt ...]`**
  Cost-gated exactly like `generate-image`. Writes N candidates to the pool at
  `<target's location>/candidates/`, updates `candidates.json`. `--target` is
  `character:<name>`, `env:<name>`, or `shot:<id>:<stage>`.

- **`ai-film review --target <target>`**
  Builds (or rebuilds) `candidates/review.html` — a static, non-interactive grid
  of every candidate image, labeled with its `id` and `parent` (if any) — and
  opens it via the OS's `open`/`xdg-open`. No network dependency, nothing leaves
  the machine.

- **`ai-film select-candidate --target <target> --id <id>`**
  Sets `candidates.json`'s `selected` field, and copies the chosen candidate to
  its canonical location: `reference.png` for characters/environments, or writes
  directly into `shot.json`'s `generation.<stage>.artifact` (via the existing
  `shot_store.save_shot`, so `status` recomputation still applies) for shots.
  This is the only command that touches anything outside the candidate pool.

- **`ai-film edit-candidate --target <target> --id <id> --instruction "..."`**
  Cost-gated. Resolves the provider for the target's capability; if it implements
  `submit_edit`, calls it with the picked candidate's image and the instruction;
  otherwise falls back to `submit()` with prompt + instruction merged. Either way,
  adds one new candidate to the pool with `parent` set to the source `id`.

None of these commands modify the behavior of any existing `generate-image`/
`generate-video`/`generate-voice`/`generate-sfx`/`generate-music`/`render`/
`status`/`validate` command — all 93 existing tests remain valid, unmodified.

## 6. Agent Conversation Flow

This section is prompt/agent design (`.claude/agents/`, `.claude/skills/ai-film/`),
not Python code — it describes how the Character/Director agent uses the CLI
commands above to conduct the actual discussion with the user.

```
User: describes character/story idea
Agent: asks clarifying questions (personality, genre, style reference —
       pure chat, no generation yet)
   ↓ converges on a brief
Agent: ai-film approve-generation --scope bibles --targets character:girl
       (cost gate — shown to user first, per the core engine's cost-gate UX)
Agent: ai-film generate-candidates --target character:girl --count 4
Agent: ai-film review --target character:girl   (opens browser)
Agent: "Here are 4 options — which do you like, or should I try again?"
User: "I like #2, but make the jacket black instead of white"
Agent: ai-film edit-candidate --target character:girl --id 002 \
         --instruction "black jacket instead of white"
Agent: ai-film review --target character:girl   (now shows 002 and child 005)
User: "005 is perfect"
Agent: ai-film select-candidate --target character:girl --id 005
   ↓ locked — assets/characters/girl/reference.png now exists
```

This loop is identical in shape for shot images, shot video, and audio — the same
four commands, only `--target`/`--stage` differ. Story/character brainstorming
(the text-only discussion that produces the brief) always happens before the first
`generate-candidates` call and involves no CLI commands at all.

## 7. Error Handling & Edge Cases

- **`select-candidate` on an already-selected target:** overwrites the previous
  selection (both `candidates.json.selected` and the canonical artifact) — the
  user is allowed to change their mind. No `--force` flag needed since selection,
  unlike generation, is idempotent and free (no new provider call).
- **`edit-candidate` on a target with no existing candidates:** errors clearly —
  editing requires a base candidate to edit; the message should point at
  `generate-candidates` as the correct first step.
- **`review` with an empty candidate pool:** errors clearly rather than opening a
  blank page — mirrors the render-preflight "no shots to render" pattern already
  established in the core engine.
- **Cost gate scope for candidates:** `generate-candidates` and `edit-candidate`
  for `character:*`/`env:*` targets use the existing `bibles` scope; for
  `shot:*:*` targets they use the existing `storyboard` scope — no new approval
  scope type is introduced. This reuses the two-checkpoint design from the core
  engine spec exactly as built.

## 8. Testing Strategy

Follows the core engine's established pattern: `Mock*Provider`-backed unit tests
for the service-layer logic (candidate pool writes, selection, edit fallback
decision), a real (non-network) test for `review`'s HTML generation, and CLI-level
tests for all four new commands using `CliRunner`, mirroring
`tests/test_cli_generation_commands.py`'s style. No real-provider tests in CI, per
the core engine's existing testing rule.

**Acceptance for the first implementation slice:**
```
✓ generate-candidates writes N candidates, blocked by cost gate until approved
✓ review builds a valid HTML file listing every candidate with id + parent
✓ select-candidate copies the chosen candidate to reference.png (character target)
✓ select-candidate writes into shot.json's generation.<stage>.artifact (shot target),
  and shot.json still validates against the existing schema afterward
✓ edit-candidate adds a new candidate with correct parent lineage
✓ edit-candidate falls back to prompt-regeneration when submit_edit is unavailable
✓ none of the 93 existing core-engine tests regress
```

## 9. Future Extensions (explicitly out of scope for this spec's first slice)

- Video/audio candidate review, using the same four commands against
  `shot:<id>:video`/`voice`/`sfx`/`music` targets.
- Whole-film final-cut preview as its own `--target final`, reusing `review`.
- Interactive (clickable) browser review, if static-gallery-plus-chat proves too
  slow in practice.
- Audio muxing into `render` and subtitle support — tracked as pre-existing known
  limitations in the core engine, not created by this spec.
